# Contract request p1-w07-3: device-bound sessions, signals, step-up and padding hand-off (no contract change)

**Status:** open, for INT-1 and the named Phase 1 work packages. Nothing for the steward:
everything below uses existing contracts (SCAFFOLD-1, p1-w01-1, p1-w06-1, p1-w07-1).

**From:** P1-W07 · **Kind:** none (integration notes) · **Owners of the follow-ups:** INT-1,
P1-W08, P1-W10, P1-W06

## Provided by P1-W07

* **DBSC** (`platform/dbsc`, `gate/auth/dbsc.go`, PCC_DBSC=1). An unbound user session's
  `/api/session`, login-finish and enroll-finish answers carry `Sec-Session-Registration`;
  `POST /api/auth/dbsc/register` (JWT in `Sec-Session-Response`, ES256 or RS256, aud = the
  URL, jti = the offer) binds the session for good: every request then needs the 10-minute
  `__Host-pcc-b` (dev `pcc_dev_b`) cookie, and the long-lived cookie alone is accepted at
  `POST /api/auth/dbsc/refresh` only (401 + `Sec-Session-Challenge`, then the signed proof).
  Challenges are single use and live 5 minutes; both endpoints are exempt from X-PCC-CSRF
  (the device signature is the proof) but keep the Origin and Sec-Fetch-Site rules.
  `dbsc/dbsctest` is the Go dev driver; `web/e2e/p1-w07.spec.ts` has a WebCrypto twin.
* **Short sessions elsewhere:** every user session starts short (12 h after its last
  passkey verification; a step-up extends it); a bound session is long-lived again
  (30 d / 14 d idle). With PCC_DBSC off every session is short.
* **Step-up** (`core.StepUp`, `gate/auth`): `Require` sets `stepup_required`, writes a
  `stepups` row (reason = the signal kinds) and publishes `SessionStepUp`; the third within
  7 days enqueues `ModSrcStepUpRepeat` (priority 3, summary `{stepups}`). `StepUpFinish`
  satisfies it. `/api/session` says `step_up: true` meanwhile.
* **Automation signals** (`gate/signals/automation`, `POST /api/signals`): client counts
  (webdriver, a driver hint, inputs per minute, visible ms) and request patterns from the
  /api hook (sustained rate or round-the-clock, feed pages without seen, tree walks and
  chain expansion at machine speed — each across several minutes of the server clock).
  Browser flags together weigh 0.5 of the 1.0 threshold and a pattern is always required,
  so assistive tech and test runners (navigator.webdriver is true under Playwright) never
  step up. Rows carry `net_h` (16-byte HMAC of the /24 or /56 under a daily key).
* **Co-signed passkey changes** (purposes `passkey_add`, `passkey_remove`): see
  `gate/auth/cosign.go`; credential-less test-hook sessions keep the P0 path.
* **Padding** (`apix/pad`): the derived set (`pad.For`; `RequestRefs` is checked against
  the OpenAPI fragments by `pad_test`), grids `pad.Default` (150 ms multiples) and
  `pad.Deep` (600 ms, then 600·k + 150 ms) for `/feed*` and `/tree/*`, a per-route
  histogram (`pad.Stats`) and `padtest.KS`, `SameBucket`, `SameHistogram`.

## Follow-ups

* **INT-1 (conformance):** run the timing KS test over the whole padded set
  (`apix.Routes()` with `Padded`) with `padtest.KS` (p > 0.01, 500 samples) and assert
  `padtest.SameHistogram` per route for found vs not-found. Expect deep pages on the
  second deep point (750 ms) the first time a reader's deep tiers are released
  (p1-w03-1), never a third one from the release alone.
* **INT-1 (journeys):** padded routes now take ≥ 150 ms (feed and tree ≥ 600 ms); a
  journey that times many feed loads should not assume sub-second pages. Passkey add and
  remove in a passkey session open the co-sign dialog (`cosign-sign`); `p0-w01.spec.ts`
  shows how a virtual authenticator signs with the previous key.
* **INT-1 (records):** with `Records.EnforceCosign` set, passkey changes of passkey
  sessions carry their assertion; adds by test-hook sessions stay unattested by design.
* **P1-W10 (account, recovery):** recovery enrollment still adds an unsigned first
  credential (a new chain); a released recovery's `RevokeAll` also ends bound sessions.
* **P1-W06:** step-up-repeat items arrive with `summary.stepups` = the count in the
  last 7 days; nothing else reads `stepups`.
* **Operators:** turn DBSC on with `PCC_DBSC=1` once served over https (the bound cookie
  is `__Host-` prefixed); browsers without DBSC keep the short session.
