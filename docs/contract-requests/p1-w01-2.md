# Contract request p1-w01-2: callers of co-signing (hand-off, no contract change)

**Status:** open, for the named Phase 1 work packages and INT-1. Nothing for the steward:
every interface below already exists (p1-w01-1).

**From:** P1-W01 · **Kind:** none (integration notes) · **Owners of the follow-ups:** P1-W02,
P1-W03, P1-W06, P1-W07, P1-W10, INT-1

`gate/cosign` is the single owner of "graph-changing writes need a passkey assertion"
(buildability C4). What it provides and what each caller does with it:

## Provided by P1-W01

* `core.CosignPurposes.RegisterPurpose(purpose, kind, builder)` — call in your `Init`. An
  unregistered purpose is `ErrNotFound` at `POST /api/cosign`, so a caller that forgets this
  fails closed.
* `POST /api/cosign {purpose, target?}` → `{intent, record, options}` and the web dialog
  `requestCosign({purpose, target?, summary?})` from `web/src/features/cosign` (resolves
  `{intent, assertion}` or `null`). Send both in your change's own request body.
* `core.Cosign.Require(ctx, tx, v, purpose, kind, body|nil, intent, assertion)` in the SAME
  transaction as the record write, then `core.Signer.Sign(ctx, tx, kind, author, body|nil,
  parties, a)`. Errors must abort the transaction (`gate.ErrNotFound` or Problem
  `passkey_rejected`).
* `core.SignupCosign` for the invitee (fidelity #21) and `NewUser.ExtID`.
* `records.Service.MyKeys(ctx)` (the signed-in user's custodial public keys) and
  `records.Service.EnforceCosign(ctx, at)` / `CosignSince(ctx)` (the co-sign cut-over).

## Follow-ups

* **P1-W02 (invites):** split `RegisterFinish` as described in p1-w01-1 ("Signup"): reserve
  the ext_id, `BeginSignup` with the Invite and Friendship bodies at `register/finish`
  (answer `{options, records}`; the join page shows them with `RecordView`), and a
  `register/cosign {assertion}` step that runs the existing serializable transaction with
  `Users.Create(… ExtID)`, `FinishSignup`, and `Signer.Sign(…, as[i])` for both records.
  Inviter side: purpose `invite_inviter` (`core.RecInvite`) before the handshake completes,
  attached to the same Invite record (Sign appends assertions to an existing record).
  New route(s) under `/api/join/*` need the steward (catalogue).
* **P1-W03 (friends):** purposes `friend_request`, `friend_accept`, `unfriend` (Revocation),
  `block` (Block); request bodies gain `{intent, assertion}` (already in plan §5.3).
* **P1-W07 (auth):** `passkey_add` — after `AddPasskeyFinish` verifies the new credential,
  co-sign its `PasskeyChange{op: add}` with an EXISTING credential (the builder reads the
  pending credential from the session) so the export chain holds; `passkey_remove` likewise.
  Enrollment (genesis, recovery) adds stay unsigned first credentials of their chain.
* **P1-W10 (account):** `account_delete`, `recovery_approve`; `GET /api/keys` may add
  `mine` from `Records.MyKeys`.
* **P1-W06 (moderation):** `mod_action` for second-moderator confirmations (ModAction draft).
* **INT-1:** once the callers above have landed, set the cut-over
  (`Records.EnforceCosign(now)`, e.g. from a `pcc keys enforce-cosign` CLI line, steward) so
  `VerifyExport` reports `missing_assertion` / `broken_chain` for later unattested records; add
  `"cosign_since"` to the out-of-band fingerprint publication.
