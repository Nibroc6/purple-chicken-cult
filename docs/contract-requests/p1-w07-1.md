# Contract request p1-w07-1: the derived padded set, DBSC in e2e runs, automation reset

**Status:** applied by the contract steward (additive) before the P1-W07 work commits.
`internal/api/apix/pad` (P1-W07) carries a pass-through stub of `For`/`Wrap` until the
work commits replace it.

**From:** P1-W07 · **Kind:** additive (apix calls a new pad function, one e2e env line,
one test-hook line) · **Implementer:** P1-W07 (`apix/pad`, `gate/signals/automation`)

## Why

1. **The padded set is derived, not hand-picked** (plan §5.1, security #19): every route
   with a `{ref}`/`{hs}`/`{id}`/`{snapshot}` parameter **or a ref in its request**
   (`POST /posts` parents, `POST /seen`, `POST /reports`, `{intent}` bodies, …), and the
   deep-tier feed/tree routes on the 600 ms grid. `apix.Route` only looked at path
   parameters and always used the 150 ms bucket. The derivation belongs to `pad` (which
   checks itself against the OpenAPI fragments in its tests), so `apix.Route` asks it.
2. **No double padding with the graph's deep-tier release** (p1-w03-1): the lazy search
   already releases the deep tiers at a whole multiple of 600 ms; a route grid of plain
   600 ms multiples would then cost a whole extra bucket for every deep page. The deep
   grid is `600 ms, then 600·k + 150 ms`: a released deep search plus ordinary handler
   work (< 150 ms) lands on the next point instead. `pad.Grid{Bucket, Slack}` carries it.
3. **DBSC in e2e runs:** `PCC_DBSC` is off by default (fail closed, D20), so the shared
   e2e server never offered device-bound sessions and `web/e2e/p1-w07.spec.ts` (which
   drives the DBSC protocol with a software device key, Playwright's Chromium has no DBSC)
   could not run against it. With DBSC on, a browser that does not register keeps the
   same short (12 h, re-verify) session it gets with DBSC off, so no other spec changes.
4. **Reset:** the automation scorer keeps per-session windows in memory; `/api/_test/reset`
   should forget them like the other in-memory state (p0-w12-2).
