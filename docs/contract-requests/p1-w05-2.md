# Contract request p1-w05-2: Web Push and server i18n hand-off (no contract change)

**Status:** open, for INT-1 and the named Phase 1 work packages. Nothing for the steward:
everything below uses existing contracts (SCAFFOLD-1, p1-w05-1).

**From:** P1-W05 · **Kind:** none (integration notes) · **Owners of the follow-ups:** INT-1,
P1-W10, P1-W06, P1-W07

## Provided by P1-W05

* **`core.Notifier` v2** (`gate/notify/push.go`): callers keep calling `Notify` in their
  transaction; nothing else changes for them. When the recipient has a subscription, a
  `push.deliver` job is enqueued in that transaction (batched kinds: with the first event
  and with each hourly `notify.flush` ping). The job re-renders the row for the recipient
  at delivery time (same horizon rules as the list: an invisible required subject, a read
  row, a deleted or suspended recipient send nothing) and sends
  `{"v":1,"title","tag","url":"/notifications"}`: `title` is
  `push.<kind>` from `internal/platform/i18n/catalogs/<locale>/server.json` in the
  recipient's `ui_locale` (`{name}` = the visible person's `@handle`, `{count}` = the batch
  size; `push.<kind>_anon` when an optional person is not visible), or only `push.generic`
  for `hide_content` subscriptions. No post bodies, no refs beyond the tag.
* **`platform/webpush`**: VAPID sender (endpoint policy, no proxy/redirects, public
  addresses only, fixed 4096-byte records), log driver, `webpushtest` fake push service
  (decrypts RFC 8291, verifies RFC 8292) for Go tests.
* **`platform/i18n`**: `ForConfig` (en, plus generated `en-XA` in dev/test), `Format`, the
  no-prose scan of push payload builders (`i18n_test.go`).
* HTTP: `GET /push/key`, `GET|POST|DELETE /push/subscriptions` (`api/openapi/push.yaml`).
  Problems `push_endpoint_invalid`, `push_keys_invalid`; `feature_disabled` without VAPID.
* Web: `/settings/notifications` (`features/push`), `src/sw/push.ts`.
* Lifecycle: `SessionEnded` deletes the session's subscriptions, `AccountDeleted` the
  account's, 404/410 the endpoint's; 5 consecutive failures drop it; ≤ 10 per account.

## Follow-ups

* **Any WP adding a notification kind** (e.g. P1-W10 `recovery_approval`, which already
  has `push.recovery_approval` / `_anon`): add `push.<kind>` (and `_anon` if the person is
  optional) to `catalogs/en/server.json` — owned by P1-W05/INT; until then delivery of
  that kind fails with `ErrUnknownKey` (logged; the in-app notification is unaffected).
* **P1-W07 (padding, step-up):** the push routes carry no `{ref}`; nothing to pad. The
  free `GET /push/subscriptions` is in the reviewed free list of the catalogue.
* **INT-1:**
  * Prod deploy needs `PCC_VAPID_PUBLIC`, `PCC_VAPID_PRIVATE` (base64url P-256 pair, e.g.
    from `webpush.GenerateKeys`) and `PCC_VAPID_SUBJECT` (`mailto:` or `https:`);
    malformed or mismatched keys refuse to start. A `pcc vapid-keys` subcommand
    (`cmd/pcc`, scaffold-owned) and a runbook entry would help operators.
  * Egress: the push sender must reach the browsers' push services on 443 (FCM, Mozilla
    autopush, WNS, Apple); the egress firewall of `deploy/runbooks/egress.md` must allow it.
  * Journey: turn push on, receive a mention through the fake push service of
    `web/e2e/p1-w05.spec.ts`, log out, receive nothing.
